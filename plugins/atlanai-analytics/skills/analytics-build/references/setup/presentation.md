# One setup presentation flow

Use the demo's presentation flow for every setup, with the actual sources and results of
the selected run. There is no separate compact setup flow or word limit. Technical stage
procedures control execution, validation and publication; these moment files control what
the person sees and how it reaches the host's visible surface.

| Moment | Presentation |
| --- | --- |
| Start | Explain the outcome, sources, steps and controls before work. A chosen demo uses its full welcome from [the demo skill](../../../analytics-demo/SKILL.md). Own-data setup uses the same structure with inspected facts; never borrow a demo's people, numbers or tour. |
| Each step starts | Show the flow's full tracker in chat and update the host task list when available, following [the checklist](checklist.md). |
| The selected collection has been checked | Review the completed collection with actual counts, check limitations and one representative definition from the accepted output. Read [context built and where to keep it](save.md) for the celebration and local-versus-shared choice through its native question delivery. |
| The context is saved or kept local | Read [ready for questions](ready.md). Show the ready block and material limitations, then supported questions immediately for both demo and own-data setup. Answer only a question the person has supplied or selected. |
| The selected questions are answered | Follow [ready for questions](ready.md) for Ask more questions, Design a dashboard and the demo's real-data continuation. |

Read the moment's file when it is reached, including on resume. Fill its values from the
selected definition, source evidence and current checks. For own data, derive the facts
that a demo's facts table supplies from those same sources. Omit a tour or example row
when there is no evidenced value; never invent one to fill the template. If only saved
queries exist, identify the representative item as a saved query and explain its SQL's business
meaning, population, source and check result without relabelling it a metric.

Build and check the whole selected collection before the review. Show a representative
metric's business meaning, calculation, population, source and actual check status as part
of that review, not as a separate checkpoint or question. Derive these from the accepted
card; no preset metric, formula or worked-example breakdown is required. A helper result,
a linked file or a note in reasoning does not show the review to the person. Full SQL and
worked examples remain available on request. If reconciliation changes the definition,
show its changed rule and check status again.

Scope still comes from the person. Demos use their preset focus and source choice; own
data uses [intent](intent.md) for missing business focus and purpose. Details-only,
survey-only and understanding-only requests stop at their requested evidence. Do not add
an extra build or save question to an already complete limited request. A chosen destination
and authorized plan do not require another approval just to display a moment.

Keep execution, source review, holds and release status distinct in every block. Partial
work still gets the celebration with honest counts. A ready block names the usable scope
and what remains unavailable; it never turns a failed check into success. Preserve the
full meaning and evidence when a host collapses intermediate updates by retaining the
selected metric's rule and status in the final handoff as well.
